# Decisions

This document records the main design decisions of EIGENHEIT. Each entry states the decision, the reason for it and its cost. Where a security choice was unclear, the option that gives more protection was chosen.

Terms used in this document:

- **Mask**: an identity. It is a set of keys created on your device. You can hold several masks.
- **Union**: a group conversation defined by a shared secret. It ends after a set term unless its members renew it.
- **Card**: the text `eigen://mask/…` that lets another person contact a mask.
- **Invite**: the text `eigen://union/…` that lets another person join a union.
- **Relay**: a server that stores encrypted messages in RAM until they expire (at most 24 hours by default).
- **Mailbox**: an address on a relay where encrypted messages are stored.
- **Cell**: the fixed-size unit of data sent between a client and a relay.
- **Blob**: an encrypted message stored in a mailbox.
- **Vault**: an optional encrypted file that stores your masks, known contact keys, the keys you marked as verified with `/trust`, and the unions you saved with `/keep`. Messages are never stored.
- **Cover traffic**: data sent on each connection to a relay at a constant rate. When there is no message to send, padding is sent, so an observer of the connection cannot tell when you send messages.
- **Burn**: delete all local data and exit (`/burn`).

1. **Direct messages use X3DH and the Double Ratchet.** Direct messages must be deliverable while the recipient is offline. X3DH starts a session without the recipient being online, and the Double Ratchet gives forward secrecy for every message. Both protocols are specified in the Signal documentation. They are implemented in this project on audited cryptographic primitives. Cost: the protocol code is specific to this project and needs an independent audit.
2. **Tor is reached through a local `tor` daemon, using its SOCKS5 port and control port.** The `tor` daemon is mature, and using it keeps the number of dependencies small. Each mask, each direct message and each union gets its own circuit through SOCKS username and password isolation (`IsolateSOCKSAuth`, which is on by default). The relay publishes an ephemeral onion service with `ADD_ONION`, so nothing is written to disk. Cost: you must run `tor`. Test status: tor 0.4.9 accepted `ADD_ONION` from `eigen-relay --onion` with cookie authentication. The SOCKS5 client is tested against a mock server. A complete round trip through an onion service could not be tested in the build sandbox, because the sandbox has no route to the Tor network. This must be verified on a real host.
3. **Direct relays are refused unless they are reached through a VPN tunnel (`--vpn`) with a relay key (`#KEY`, see entry 34), or `--i-accept-the-risk` is set.** This option is intended for local development. Without a relay key, a direct link has no link encryption, and a network observer can see the mailbox IDs. Message content remains end-to-end encrypted.
4. **All traffic uses fixed 1024-byte cells, with one response for each request.** The relay answers every request cell with exactly one cell, so the amount of data received equals the amount of data sent. FETCH returns one blob at a time.
5. **Every blob is exactly 960 bytes.** Before encryption, each plaintext is padded to a fixed size for its message type. Messages that are too long are rejected and are not split, so the length of a message is never revealed. Maximum text length: 460 bytes in direct messages and 560 bytes in unions.
6. **The relay never sees the sender (sealed sender).** The wire format has no sender field. The first X3DH message encrypts the sender's identity to the recipient's signed prekey (ECIES). The relay sees only random-looking bytes in the recipient's introduction mailbox.
7. **Mailboxes change regularly.** The receive mailboxes of a direct message are announced inside the ratchet payload. A new one is created at every DH ratchet step, that is, whenever a side starts a new sending chain. Old mailboxes are still polled for 15 minutes. Union mailboxes change every hour: `id = BLAKE2b-MAC(S, "eigen/umbox" ‖ hour)`.
8. **Message headers are hidden from the relay by an outer AEAD layer.** The key for this layer is derived from the announced mailbox secret, so each mailbox has its own key. This hides ratchet headers from the relay and keeps the code simple.
9. **Unions use sender keys.** Each member encrypts with its own sender-key chain and signs every union message with its mask key, so members cannot forge messages in the name of other members. Cost: post-compromise security in unions is limited. MLS (RFC 9420) is planned for a later version.
10. **A vote to remove a member (drop) passes with a strict majority of the remaining members.** The target of the vote is not counted. With this rule, one member cannot block a removal, and a minority cannot force one. A drop replaces the keys without the target for the current term only. The target can return with another mask. No ban list is kept after the term ends.
11. **A union ends at the earliest end time reported.** A new member adopts the smallest `ends_at` value among the HELLO messages it receives. A union ends unless its members renew it, and no member can extend a union for the others.
12. **Each member renews individually.** `/renew` commits only the member who runs it to the next term. At the end of the term, members who did not renew are removed, and the remaining members replace the keys.
13. **Names have the form `adjective-noun-xxxx` and are derived from BLAKE2b(ed25519 ‖ context).** A name contains 8 + 8 + 16 = 32 bits. Names are easy to read, but 32 bits are few enough that an attacker can create a key with the same name. Names are therefore only labels. Keys are authenticated by trust on first use (TOFU) and by `/verify`, which shows the full fingerprint and a short authentication string (SAS).
14. **PGP is supported only for key export and import.** The format is OpenPGP v4 with an EdDSA-legacy Ed25519 key, a self-signature and the SHA-1 v4 fingerprint that OpenPGP requires. PGP is not used for sessions, because it has no forward secrecy, uses long-lived keys and its packets carry a lot of metadata.
15. **All formats are hand-written, length-checked binary formats (`wire.rs`).** Serde is not used. This keeps the number of dependencies small and makes every size explicit.
16. **Secrets are cleared from memory, and memory is locked when possible.** Secrets are overwritten with `zeroize` when they are dropped. `mlockall(MCL_CURRENT|MCL_FUTURE|MCL_ONFAULT)` is called only if `RLIMIT_MEMLOCK` is unlimited or can be raised to unlimited, because a partial lock can make later allocations fail. Otherwise, secrets may be written to swap, and the status bar shows `Memory not locked` if the terminal is wide enough. Core dumps are disabled, and the process is marked as non-dumpable (`PR_SET_DUMPABLE=0`).
17. **Ratchet sessions are never saved, even when a vault is used.** The vault stores masks, union secrets, TOFU pins and the keys marked as verified with `/trust`. After a restart, direct messages start with a new handshake. Saved ratchet state would remove forward secrecy if the disk were seized.
18. **The vault has two slots of equal size.** One slot holds the real data. The other slot holds a decoy or, if it is unused, random bytes. The duress passphrase opens the decoy. If the decoy is marked `wipe`, opening it overwrites the other slot without any notice.
19. **Proof of work (PoW) is a BLAKE2b hashcash bound to `(hour, mailbox, H(blob))`.** Relays require 12 bits, plus 2 bits for each doubling of the PUT rate on a mailbox. Unions require 14 bits for messages by default, and 6 additional bits for JOIN.
20. **Relay panics produce no output.** The relay installs an empty panic hook, and release builds use `panic = "abort"`, so a crash message cannot reveal identifiers.
21. **A new mask is created with `/mask`.** Most terminals send the same key code for `Ctrl-M` and `Enter`. `Ctrl-M` therefore creates a new mask only in terminals that support the kitty keyboard protocol.
22. **Each relay is routed according to its address type.** Connections to `.onion` relays always go through the Tor SOCKS proxy, with a random username for each context: the mask's introduction mailbox, each direct message and each union. Each context therefore uses a separate circuit. Direct relays are connected without Tor, either through the VPN interface or, with `--i-accept-the-risk`, without a tunnel. A direct connection is never used inside a Tor context.
23. **A union is saved only when you request it with `/keep`, and only with `--vault`.** The vault stores the union secret and the mask used in the union. It never stores messages or the member list (roster). After a restart, the client rejoins the union with a new JOIN.
24. **The vault file is written in place, followed by `fsync`.** No temporary file or rename is used. `/burn` overwrites the file twice with random bytes and then deletes it. On SSDs, on copy-on-write file systems and with snapshots, old data blocks may remain on the disk. Use full-disk encryption on the disk that holds the vault.
25. **The clipboard is used only when you ask for it.** `/copy` and the `C` key on the card or invite screen put the text on the terminal clipboard with OSC 52. Inside tmux, the text is passed through to the outer terminal. The clipboard is cleared after 30 seconds, on `/burn` and when EIGENHEIT exits normally. EIGENHEIT never reads the clipboard. Copying works only in terminals that support OSC 52. A clipboard manager on your system may keep its own copy of the text.
26. **Cover traffic sends cells at a fixed rate.** With cover traffic on, every link sends exactly one cell every 500 ms ± 30 %, either a real cell or padding. When there is a lot of activity, messages are delayed so that the traffic pattern stays the same. With cover traffic off, each PUT waits a random delay of 0 to 1500 ms.
27. **The union secret is replaced whenever a member leaves or is removed (rekey).** The new secret, with new mailboxes, a new control key and a new union ID (`uid`), is sent only to the remaining members. Former and removed members can no longer see how many messages are sent. The member with the lowest key sends the new secret first. This order only decides who acts first and gives that member no special rights. If that member does not send it, any other remaining member does. When several rekeys happen at the same time, all members reach the same result. Cost: old invites stop working. `/invite` shows the current invite.
28. **New members cannot see who was in a union before them.** JOIN messages carry a signed timestamp, and outdated JOINs are ignored. A HELLO message is processed only by the member it is addressed to. Without these rules, a new member could read the messages stored on the relay and learn who had been in the union earlier.
29. **The screen can be hidden and locked locally.** Screen hiding (`/veil`) hides message text, the names in the side panel and the conversation titles. The status bar still shows the name and glyph of the active mask. Screen hiding is turned on with `Ctrl-V` or `/veil`, or automatically after 5 minutes without input. If the terminal is wide enough, the status bar shows `Screen hidden`. `/veil off` turns off automatic hiding. The key press that ends screen hiding is discarded, so no text is typed by accident. `/lock` stores only an Argon2id hash of the passphrase. After five wrong attempts, all data is deleted and EIGENHEIT exits. `/deadman` (auto-burn) deletes all data and exits after a chosen time without input. If the terminal is wide enough, the status bar shows `Auto-burn in HH:MM:SS`. The lock passphrase is never stored in the input history.
30. **`/unsay` and `/once` depend on the recipient's client.** The other person's client removes the message. Disappearing messages work the same way. Removal is not guaranteed, because a modified client can keep the message. The interface therefore reports that a message was taken back and does not say that it was deleted.
31. **`/trust` is a private mark.** The ✓ mark means that you compared the SAS with the other person through a separate channel. It is stored only in your vault, if you use one, and is never sent to anyone.
32. **I2P is reached through the SAM v3 bridge of a local router.** A local router (i2pd or Java I2P) builds the tunnels. EIGENHEIT implements only the SAM text protocol and needs no additional crates for it. Each link context (the mask's introduction mailbox, each direct message and each union) creates its own TRANSIENT destination with its own tunnels. The relay also publishes a TRANSIENT destination. It discards the peer destination line that SAM sends when a connection is accepted. Test status: a real i2pd 2.x router answered the SAM handshake. `SESSION CREATE` waits until tunnels are built, and this was not possible in the sandbox because it has no route to the I2P network. The complete flow is tested against a scripted SAM bridge.
33. **A VPN or WireGuard tunnel is used by binding sockets to its interface.** `--vpn wg0` (alias `--wireguard`) binds every direct socket to the interface with `SO_BINDTODEVICE`. If the tunnel is down, connections fail and no traffic leaves through another interface. This acts as a kill switch for each socket. EIGENHEIT contains no WireGuard implementation of its own, which keeps the code small. Relays must be given as IP addresses, because resolving a host name would send a DNS query outside the tunnel. Interfaces that do not appear to be tunnels are refused unless `--i-accept-the-risk` is set.
34. **Direct relay links are encrypted with Noise.** A VPN hides your IP address from the relay. It does not hide your traffic from the VPN provider. Cells are not encrypted on the wire by themselves. Tor and I2P encrypt their own links. Direct relays therefore use a `Noise_NK_25519_ChaChaPoly_BLAKE2s` link (`snow`, with ChaCha and BLAKE2 only). The relay prints its address as `IP:PORT#KEY`, and the client authenticates the relay with that key. Every cell is sent as a fixed 1040-byte frame. Without `--i-accept-the-risk`, direct relays are refused unless both a tunnel (`--vpn`) and a key (`#KEY`) are given. The relay's link key and onion address are both ephemeral. The relay creates new ones each time it starts.
35. **Transports can be combined.** `--relay x.onion:7777 --relay y.b32.i2p --relay 10.8.0.1:7778#KEY --vpn wg0` uses all three routes. The status bar lists each route, for example `Tor+I2P+VPN wg0 ●`. The route label is shown in the accent color if any route is exposed, that is, if it is a direct connection or a VPN route without encryption.
